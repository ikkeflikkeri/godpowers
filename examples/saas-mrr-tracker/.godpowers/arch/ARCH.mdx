# MRR Tracker Architecture

## Options Considered

| Shape | Score | Why rejected | Trap flag |
|-------|-------|--------------|-----------|
| Local web app over an exported JSON file (baseline) | 8.3 | [DECISION] Chosen, because local import satisfies the Privacy NFR and the weekly review scope without network credentials. | [HYPOTHESIS] Hidden cost: account changes after export stay invisible until the next local import. |
| Live Stripe OAuth with a hosted sync worker | 6.9 | [DECISION] Rejected, because a hosted worker would move customer account names outside the local workspace, contrary to the Privacy NFR. | |
| Stripe webhook receiver with a persistent event store | 5.8 | [DECISION] Rejected, because P-SHOULD-01 asks for a weekly summary, so streaming ingestion adds public ingress and replay handling without improving that weekly flow. | [HYPOTHESIS] Hidden cost: a webhook receiver must be publicly reachable and replay-safe, which is more operational surface than a weekly review workflow justifies. |

[DECISION] Scores include trap demotion and use the NFR map below; novelty is
not a scoring axis.

## System Context

[DECISION] MRR Tracker runs as a single local web app that imports Stripe subscription events, computes weekly movement buckets, and renders a founder review dashboard.

## Containers

- [DECISION] The ingestion container reads Stripe subscription events from an exported JSON file during the example flow.
- [DECISION] The movement engine container normalizes subscription deltas into new, expansion, contraction, and churn buckets.
- [DECISION] The dashboard container renders bucket totals and account drill-down tables.

## Critical Flows

```
Weekly import and review (crosses the local-file boundary, touches 3 containers)

1. Founder          -> ingestion         select the exported Stripe JSON file
2. ingestion        -> movement engine   emit normalized subscription deltas
3. movement engine  -> local workspace   WRITE account deltas and bucket totals
4. movement engine  -> dashboard         serve bucket totals and drill-down rows
5. dashboard        -> Founder           render the weekly review
```

| Flow | Crosses | Writes at | Fails visibly at |
|---|---|---|---|
| Weekly import and review | local-file boundary | 3 | 2, before anything is written |

[DECISION] The import writes only at step 3, so a malformed export leaves the
previous week's totals intact rather than half-replaced.

## NFR-to-Architecture Map

| NFR | Architectural choice |
|---|---|
| Accuracy | [DECISION] The movement engine stores each account delta and sums buckets from those deltas so totals can be reconciled within 1 dollar. |
| Privacy | [DECISION] The example keeps imported Stripe data in the local workspace and does not send account names to a hosted service. |

## Capacity Envelope

| Input | Today | At the PRD horizon | Source |
|---|---|---|---|
| Subscription events per export | 1,200 | 12,000 | [HYPOTHESIS] a 300-customer account at 40 events per customer per year; validate against a real export before the first release |
| Imports per founder per month | 4 | 4 | [DECISION] one weekly review, by design |
| Account delta rows retained | 1,200 | 144,000 per year | derived: 12,000 events per import, twelve months |

| Container | Derived load | Headroom |
|---|---|---|
| ingestion | 12,000 events parsed per import, four times a month | [DECISION] one single-pass JSON read on a laptop, orders of magnitude below any limit that binds |
| movement engine | 144,000 delta rows summed per dashboard load | [DECISION] fits in memory; the sum is linear in rows |
| dashboard | one founder, one session | [DECISION] no concurrency to plan for |

[DECISION] Saturates first: the movement engine, once retained delta rows pass
roughly 2 million, which at this import rate is about fourteen years out. That
number, not a user count, is what ADR-001's flip point should name.

## Failure and Degradation

| Dependency | Timeout | On failure | Idempotent | Founder sees |
|---|---|---|---|---|
| Exported JSON file | 30s read | [DECISION] Abort the import and keep the previous totals | Yes; re-importing the same export produces the same deltas | The parse error and the line it stopped on |
| Local workspace store | 5s write | [DECISION] Roll back the import; no partial bucket totals | Yes | "Import failed, showing last week's review" |
| Stripe, the export's origin | none; offline by design | [DECISION] Nothing to fail, because the app never calls Stripe | n/a | Staleness, stated as the export date on the dashboard |

[DECISION] Backpressure: one founder importing one file at a time, so a second
import is rejected while the first holds the workspace lock.

[DECISION] Recovery: re-run the import. The workspace still holds the last
successful totals, so recovery is one action and needs no cleanup.

For each container, what happens if it dies:

| Container | If it dies | Verdict |
|---|---|---|
| ingestion | No new imports; the last totals still render | [DECISION] Degrades, does not stop |
| movement engine | The dashboard has nothing to serve | [DECISION] SPOF, accepted: a local single-user app restarts with the process |
| local workspace | Totals are unreadable until the file is restored | [DECISION] SPOF, accepted: the export file is the source, so a re-import rebuilds it |
| dashboard | The founder sees nothing | [DECISION] SPOF, accepted: same process, same restart |

## Tradeoffs

[DECISION] The example uses local JSON import instead of live Stripe OAuth because the Privacy NFR keeps account names local, and instead of webhooks because the weekly review flow does not need streaming ingestion.

## ADR-001 Local Stripe Export

[DECISION] ADR-001 chooses local Stripe JSON export because it beats hosted OAuth on the Privacy NFR and beats webhook ingestion on the weekly review scope; the tradeoff is snapshot staleness between imports.
